# Finish check — design

For `claude-code` and `codex`; the evidence is in
[research/harnesses](https://github.com/rajasdevel/outcomebound-research/tree/main/harnesses).

## Outcome

In `claude-code` or `codex`, when a turn ends on a working tree the project's Done commands have
not been checked on, those commands run in the background, the turn end waits for none of them,
and a failure goes back to the agent as something to fix, so the run continues instead of ending
on an unchecked "done". The invariant the hook holds: a turn that ends on a changed tree reads as
checked only where the Done commands passed on that tree; a failure goes to the agent at most once
in a session for each failure signature, and only from a run that session started, unless adopt
measured it as a known failure on a commit this checkout descends from and it fails the same way
(the record of known failures is in no committed file), or it was seen on the tree the turn began
with; and a Done that does not run, does not finish, or ran on a tree that changed before it ended
reads `UNVERIFIED`. The
[constant-time stop](#constant-time-stop) holds how, and where it and a row below disagree, it
decides. The kernel's Done line
becomes a check the harness runs (S2, S5). The hook fires at every turn end and returns
within seconds, so a turn that changed nothing reruns nothing, whatever the last verdict was. A command that already failed when
adopt measured Done, on a commit this checkout descends from, holds no turn while it fails the same
way; any other failure holds, once for each signature in a session. A turn that changed nothing
since its first prompt holds nothing of its own; the one hold it can carry is the delivery of a
failure that an earlier turn of the same session made and no wake delivered. A failure the
working tree already had when the turn began, with the same signature, is reported and not held,
so the hold is for what the turn could have caused. The hook
checks the checkout at the working directory its input names, and no other. The project sets how
long Done may run (maintainer, 2026-10-04). Optional and removable, as every adopt write; every other harness is named as not
available yet. How: `outcomebound finish-check`, the verb the entry calls, and
`outcomebound_tools/adopt.py`, which writes the entry.

| The time limit and a stop from outside end the whole tree on every platform. A command starts in its own process group: a new session on POSIX, `CREATE_NEW_PROCESS_GROUP` on Windows. At the limit, or on Ctrl-C or SIGTERM, POSIX sends `SIGKILL` to the group. On Windows the command also joins a job object of its own, before it runs. `programs.start_tree` starts every command. It loads the job API first (`ctypes` and `kernel32`), so that no load happens while the command runs. It then starts the command with `CREATE_SUSPENDED` added to the creation flags. `programs.track_tree` makes the job and joins the command, with `kernel32` only: `CreateJobObjectW`, `SetInformationJobObject` with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and no breakaway flag, and `AssignProcessToJobObject` with the handle that `Popen` holds. Last, `start_tree` resumes the command. The resume uses the documented thread calls: `CreateToolhelp32Snapshot` with `TH32CS_SNAPTHREAD` lists the threads of the system, and `OpenThread` and `ResumeThread` run each thread that the command owns. A command that starts suspended has one thread, and `ResumeThread` must return 1 for it: the suspend count of a thread that has run nothing. Any other count is a failed resume. `Popen` closes the handle of that thread when it returns, so the thread must be found. `NtResumeProcess` in `ntdll.dll` takes the process handle that `Popen` keeps and needs no list. It is not in the Win32 reference, so it was not chosen. Each process that the command starts joins the job too, from its first instruction. Where no job API loads, the command starts at once, without the suspended flag, and `stop_tree` uses `taskkill`. At the limit, or on Ctrl-C or SIGTERM, Windows calls `TerminateJobObject`, which ends every process of the job at once. Where no job holds the command (the API cannot be loaded, or the process cannot join a job, for example a job that refuses nesting) or `TerminateJobObject` fails, Windows falls back to `taskkill /T /F /PID <pid>`, named by its `System32` path, and then kills the process where `taskkill` could not run. No call can raise out of the stop. `stop_tree` returns the path that ended the tree: `job`, `taskkill`, `kill` (the process alone), or `group` (POSIX). On Windows the time-limit reason of the finish check names it, for example `stopped at the time limit after 5 s, by its job` (or `by taskkill`, or `by a kill of the command alone`), so that a command that outlives a stop shows which path ran. The limit test in `tests/test_finish_check.py` asserts `by its job` on Windows. The Cygwin and MSYS2 runtimes add `CREATE_BREAKAWAY_FROM_JOB` to a process they start only where the job they run in allows breakaway. This job never does, so no descendant of a shell leaves it. `programs.py` owns the job of a process. Each caller that starts a command (the finish check, and so the measurement of `adopt --finish-check`; the validation verb; the explorable browser runner; the eval runner's bounded command) calls `start_tree` in place of `Popen` and `stop_tree` to stop the command, and holds no job code of its own. A caller that gets an `OSError` from `start_tree` reads it as a command that could not start, as for `Popen`. The job closes when the engine lets the command go, and a job whose last handle closes ends what still runs in it. So a process that a command leaves behind after it ends by itself is ended then, and an engine that is ended from outside takes the tree with it. The suspended start closes a race. Before it, a process that the command started between `CreateProcess` returning and the join was outside the job, and `TerminateJobObject` did not reach it. That time was a few calls of one thread, and the first call of a run also loaded `ctypes` and `kernel32` in it. Now nothing of the command runs before the join. A failure never leaves a command suspended. A join that fails (no job could be made, or the command cannot join one, for example a job that refuses nesting) does not stop the command. The command is resumed, runs without a job, and `stop_tree` uses `taskkill`. A resume that fails, or raises, ends the command: its job where it joined one, else `taskkill`, and `Popen.kill` last. `start_tree` then raises `OSError`. A `KeyboardInterrupt` or a signal handler's exception between the start and the resume ends the command in the same way before it goes on. One time is open: an exception raised inside `Popen` itself, after the process exists and before `Popen` returns, leaves a suspended process that nothing holds. The finish check holds its stopping signals across the start, so it is closed there. The other callers do not hold them, and the time is a few instructions wide. A stop that arrives while a command starts is held until it has started, as on POSIX. On Windows the held stop is never sent to the engine itself with `os.kill`, which there ends the process at once with the signal's number as its exit code, running no `finally` and so leaving the command's tree running: Ctrl-C is the exception Python raises, and another signal exits 128 plus its number, after the tree is stopped. A hosted Windows run of the limit test in `tests/test_finish_check.py` (its command starts a grandchild and records the Windows process id) passed with `taskkill` alone. A later run (Python 3.10) failed it: the grandchild still ran 10 s after the stop. It did not fail on every run. The cause of that miss was `UNVERIFIED`. The first guess was that `taskkill` finds a tree through parent process ids and has a 10 s limit here, and either could miss a process on a loaded machine. After the job was added, a run of the main branch (hosted CI run 37921045557, Windows, Python 3.14) failed the same test: the stop at the time limit happened, and the grandchild ran 10 s later. ## Constant-time stop

A hook that costs time or tokens and catches no defect is a defect of the hook. Measured in
adopting projects: Done ran in the stop at every turn end that changed the tree, 3 to 5 minutes
each, 16 times in one week, and found no failure, while the person waited for each; and an
environment crash (a wrong Python on the hook's PATH) was held as a test failure 3 times, which

class: no turn end waits for Done. They bound the holds, and do not remove them as a class: a
failure goes to the model at most once for each signature in a session, never where the tree the
turn began with was seen with it, and never from another session's run. Where a row above and a
row here disagree, this section decides; the implementing change edits the row above in the same

## Edges

adopt rewrites bytes it did not write in one place: a settings document's whitespace, when it
adds or removes its entry. The entry is one more committed hook a pull request's review must
read: `claude-code` trusts a folder once and never reviews a changed entry. The entry runs with
the person's privileges and without the permission prompt the agent's own command would meet; it
is committed, so every teammate's harness runs it after its own accept. A harness launched from
a desktop without `outcomebound` on its PATH shows a named hook error and holds nothing; one
that never fires the hook fails silently, as the install report says. Where a command's output names no
failure ids a known failure covers the whole command: while it fails with its recorded exit code,
a new failure inside it holds nothing, and the person sees it only in the `systemMessage`, which
says `known by its exit code only`. A Done split into narrower commands narrows that, and
`adopt --finish-check` measures Done again. adopt measures in the person's shell, while the hook
runs with the harness's PATH; a command that fails at install for a reason of that shell alone is
kept as known, and a failure with the same exit code and no ids is then silent in the hook. The
record of known failures keeps a pull request out, not the session's agent: an agent that can
write the Git directory can write the record, as it can edit the manifest's Done or the hook
entry, and the record is in no diff a reviewer reads. The agent can also reach the same end through
a sanctioned command: run `adopt --finish-check` after its change broke code, and its failures
become known in a record that replaces the honest one. What guards both is visibility: a known
failure goes to the person with its output and its commit, on `codex` at the stop and on
`claude-code` at the next prompt, through the turn-start entry's `systemMessage` (`UNVERIFIED`
until observed; else only when the person runs `outcomebound finish-check --status`, which is
weaker), and a measurement that
replaces a record names each failure new since it. A known failure that a later commit fixed, with
no turn end since on a tree where the command passed, stays in the record: if the agent breaks it
again with the same exit code and failure ids, it is not held. A pull does not measure again;
`adopt --finish-check` after it does. A mixed selection installs
the entry where a row has one and names the rest; with no selected row that has one,
`--finish-check` is refused.

What each verdict reads, and who writes it (`outcomebound_tools/finish_check.py`). The hook's
input on stdin (`cwd`, `stop_hook_active`, `background_tasks`, `session_crons`) is the harness's.
The Done commands come from the manifest, which the change under check can write; they run only
while their digest equals the one in the committed hook entry, so a changed Done list runs
nothing and reads `UNVERIFIED`, unheld, to the person. That is flagged, not held: a hold cannot
tell a planted list from a new one, and the instruction audit keeps the entry a review hit that
quotes the Done commands. The timeout is the entry's own, also committed. The known-failure
record is in the Git common directory and the checked-tree record in the Git directory, neither
committed: adopt writes the first and the verb edits it, since a known command that passes leaves
it; the verb writes the second. A pull request can write neither, and an agent in the session
can, as the paragraph above says. The [constant-time stop](#constant-time-stop) adds four files to
the Git directory, none committed: the run lock, the run record and the stuck note, which the run
writes, and, in the Git common directory, the held list, which a hold writes. The held list decides only whether a
failure goes to the agent or to the person; the run record decides which tree and session a
verdict is for, whether a run is alive, and which process a superseding run ends,
read only while that process holds the lock. An agent in the session can write both, as it can
write the checked-tree record, and a pull request can write neither. The run is the one process
the hook leaves running after a turn ends, and it can outlive the session: one for each checkout,
by the lock, and no longer than the time limit.

## Runtime portability

The hook uses the installed engine's Python and standard library, Git for working-tree identity,
and the supported POSIX shell for the project's Done lines: the system shell on POSIX, or the
shell supplied by Git for Windows. Windows process cleanup uses a job object, which the
standard library's `ctypes` reaches in `kernel32`, and falls back to the operating system's
taskkill. The hook does not need a package manager, sg, Docker, Node, a network fetch or the
engine's development tools. A Done command can require a tool for its own work; that requirement
belongs to the project and is not installed or bypassed by the hook.

Shell selection and missing-tool checks use the environment in which Done runs. An absence
probe must finish within the remaining command time. A probe that cannot start, times out or
returns an unrelated failure does not confirm that a tool is missing and does not convert the
original failure into an environment exception. A confirmed unavailable external tool remains
UNVERIFIED and is not cached as a successful check.

Shared hook entries keep the portable command name, never one machine's environment path.
Explicit finish-check measurement reports when that command is absent from its reduced hook
environment. This is a setup diagnostic, not proof of a desktop process's actual PATH or native
hook execution, and it changes neither the Done verdict nor the trust decision.

## Lifecycle qualification

v1.5.0 qualified the native prompt/Stop/retry chain for each harness for which that behavior is
claimed. This is separate from direct verb tests and the isolated model-evaluation runner. The
[native observations in E21](../../evaluations.md#separate-native-hook-observations) hold the
result and its limits.

| Decision | Rejected alternative | Owner | Status |
| --- | --- | --- | --- |
| A native observation binds the harness release, installed hook bytes, target checkout, effective tools, prompt mark, Stop result and retry behavior to the same test | configuration or unit tests claimed as an observed native event chain | agent | decided |
| Required native trust remains the person's act. Without a usable native session, the relevant claim is UNVERIFIED and is not advertised as qualified | editing trust state or bypassing the harness to make the check pass | agent | decided |
| An observed retry or PATH defect is repaired with a synthetic regression while preserving the gate invariant and its data ownership | recording a new known failure or loosening the hold to conceal the defect | agent | decided |

The existing completion commands, read sets, writers, exits and known-failure semantics stay as
specified above unless a reviewed change explicitly updates them. Any narrowed finding or new
exemption carries the required independent adversarial review.
