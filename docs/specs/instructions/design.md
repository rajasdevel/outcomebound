# Instructions — design

## Outcome

Before a model reads a project's instruction files, a person can see what in them, or in the
harness settings beside them, could steer an agent unseen, and whether the loading facts behind
that reading are current. The invariant the command holds: each file or setting in scope that
could steer an agent unseen is reported on every run, as a FAIL, a review hit or `UNVERIFIED`,
and data in the target can decide only whether a review hit of those checks changes the result,
as the rows below say, never whether it is reported. It also reports, without changing its result,
each path, Make target or package script that project-owned instruction text names and the target
no longer holds; and, as a FAIL, each place where a Markdown or text file Git lists still names a
term, path or command the project's own `.outcomebound/retired.json` retires. For that check alone
the project's data decides what is read: the list's `scope`, `history` and `allowed_in` patterns
say where the check looks and where a retired term may stay. The command reads and reports; what a hit means is the person's call.
How: `outcomebound instructions check --help` and `outcomebound_tools/instruction_audit.py`.

| A third family, `references`, first with one check, `stale-reference`, now with `retired-reference` beside it (rows below): a path, a Make target or a package script that project-owned instruction text names and the target no longer holds. Measured studies of context files found stale code references in many repositories, and an agent follows a command or path a file names: this answers a failure seen in projects' files, which the agreement and wording checks above did not. It answers to rule S14 (agreement), second in the standard's severity order. `stale-reference` never changes the result (`decides: false`), so a healthy project's exit does not move, and it rules nothing safe; it is reported for the person and the agent, as the ancestors hit is. The report's schema gains `references` in its `family` and `check` values and its `counts`, a wire-format change this row decides. Its reads widen the command's outcome from what could steer an agent unseen to what in that text has gone stale too | the reference check in `adopt --check`, which reads the install's own records and the hook files adopt writes, never instruction prose; a hit that changes the result, which would make exit 2 constant on projects whose text names a path a build creates; a model that judges whether a reference still holds | agent | decided |
| A second check in the `references` family, `retired-reference`, reads the project's own list of retired terms, `.outcomebound/retired.json` (`schemas/retired-terms.schema.json`): each entry names a process term, a path or a command, how it is matched, the day it was retired, what replaces it, optionally why, and the files where it may still appear; the list may also name the files the check reads (`scope`) and the files that hold history for every entry (`history`). A fact owned elsewhere and restated in prose goes stale when the owner changes: in adopting projects, process cuts left disagreements across a project's contributing guide, guides and playbook; its retired runtime names had a check, its process terms had none. `adopt` never edits a project's `CONTRIBUTING.md`, and `stale-reference` reads only paths, Make targets and package scripts in instruction files, so neither catches a retired process word. The check reads every file Git lists (tracked, or untracked and not ignored, as the other checks read) with the extension `.md`, `.mdc`, `.markdown`, `.txt` or `.rst`, not only instruction files, since the stale copies were in documents a person and an agent read for process; a target Git cannot list is walked whole, as for the other checks. The list's optional top-level `scope`, path patterns, narrows that to the files it names, so a monorepo or a project with vendored documents and licences keeps the check to its own text; without `scope` every listed text file is read. The project's own `.outcomebound/fragments/local.md` is read, by name, since the `Changed —` line lives there; only the skill and fragment copies the manifest records are left out. An occurrence is a FAIL (it changes the result, exit 1), since the project itself declared the term retired: no reading of the check can be wrong about what the file says. The list is the project's file, never an install record: a project with no file has no finding, and an unreadable or invalid file reads `UNVERIFIED` with the reason, once. `--only CHECK`, repeatable, limits a run, its report and its exit to the named checks, so a floor `exit` claim can run this check alone and no other check's review hit moves its exit; the [floor design](../floor/design.md) says how `floor propose` offers it (agent, 2026-10-15, within the maintainer's directive to remove the class: a FAIL over a review hit, and the scope, are reversible) | a new verb for the list, whose reads and report would be the audit's own; a review hit that does not change the result, which a person reads past as the 16 copies were read past; reading instruction files only, which misses the guides and playbooks where the copies were; terms in the manifest, which adopt owns and a person's retirement is not; a model that judges whether a sentence still describes the retired process | agent | decided |
| What `retired-reference` does not count. (1) Case and boundaries. An entry's `match` is `exact` by default: the term as written, save that the first letter of a `term` entry matches in either case (a sentence start); `ignore-case`, which an entry names, matches in any case. Common words make poor exact terms too, and `floor propose` prints the count of current occurrences before it offers the claim, so a person sees what retiring a word costs. A leading `./` on a `path` occurrence is read away first; then an occurrence counts only where the character before and after it is not a letter, digit, `_` or `-` (so `review` in `reviewer` or `pre-review` is no `review`), and for a `path` entry not `/` or `.` either, save a full stop that no word character follows, so `docs/old.md` is not found inside `docs/old.md.bak` and is found in `see docs/old.md.` A sentence start, where an exact `term` entry's first letter matches in either case, is after `.`, `!` or `?` (closing quotes, brackets or emphasis allowed between), at the start of the text, a paragraph, a list item, a heading, a quote or the first table cell, or at the start of a line after a line that ends a sentence; a later table cell, and the first line after a heading with no blank line between, are not one. A space in the term matches any run of whitespace, a line break included, or one `-`, so a phrase that a Markdown file wraps, and its hyphenated form (`release notes`, `release-notes`), are both found. (2) Code: a `term` entry is read in prose only, never inside an inline code span or a fenced or indented code block (four columns after a blank line or code; an indented block inside a list item is the item's text), which quote literal text (a log line, an old command's output); a `path` or `command` entry is read in prose, code spans and fenced blocks, since that is where an agent finds a command to run. (3) History: a released section of a `CHANGELOG.md` (any folder, the name in any case), from a level-2 heading that holds a version (`## 1.2.0`, `## [1.2.0] - 2026-10-01`) and not the word `Unreleased` to the next level-2 heading, is history for every entry; so is each file the list's top-level `history` patterns name (decision logs, ADRs), and each file the entry's own `allowed_in` names. (4) A quote in a `Changed —` line: on any line that starts with `Changed` followed by a dash (after a list marker, emphasis or nothing; an em or en dash may touch the word, while `-` and `--` need a space before them), the dated line the lifecycle reference adds to the `local` fragment's Context, text in double quotes (straight or curly) or a code span anywhere in that line's paragraph is the record of what changed and does not count: on the `Changed` line, on a line it wraps onto, and where a quote runs on across a soft line break; the same words outside the quotes count. The lifecycle templates show the quoted form (the [lifecycle design](../lifecycle/design.md) names the text). (5) Not read: OutcomeBound's managed blocks, the skill and fragment copies the manifest records (the project cannot edit them; the project's own `local.md` is read, also where `scope` leaves it out), a file the harness table records as one person's (`CLAUDE.local.md`), `.outcomebound/retired.json` itself, what Git ignores, and what `scope` leaves out. A `scope`, `history` or `allowed_in` pattern with no `*` or `?` names a file or a folder, and so also each path under that folder (`docs` reads `docs/a.md`); a file that `history` names is not opened. (6) Readings the rules give that a reader may not expect, each by the rules as written: a `term` counts inside a URL's hyphenated path (`https://x.io/review-board/` for `review board`, since a space matches `-`), in a file name (`standup.md` for `standup`, since `.` is no boundary for a term), in a fenced block inside a blockquote, which is read as the quote's prose, and in an indented code block inside a list item, which is the item's text. Each occurrence names the file, the line, the entry's term, its retired day and `replaced_by`, so the fix is in the report | case-insensitive matching by default, which makes a common word a gate that fails ordinary prose (a retired `review` would fail "we review"); fully case-sensitive terms, which miss a term at the start of a sentence; reading what Git tracks only, which passes an untracked new guide locally and fails it in CI after `git add`; every occurrence including code, which flags quoted output that records the past; a history list fixed by the engine, which cannot know where a project keeps its decisions; reading the `Changed —` line whole, which lets any prose on it keep a retired term | agent | decided |
| A target that Git refuses as owned by another user (`dubious ownership`, as in a container whose root runs over a checkout another user made) is walked whole, as a target Git cannot list is, and the report's listing line says that Git refused it and names the command that trusts it (`git config --global --add safe.directory <the target>`). The engine's Git reads never pass `-c safe.directory`: `safe.directory` exists so that a repository another user owns cannot run its own code under yours, and the read-only configuration (`GIT_READ_CONFIGURATION`) closes `core.fsmonitor`, the pager and the external diff only, not every command Git runs for a repository, such as a clean or smudge filter a `.gitattributes` file names. Trusting a target for Git is the person's act, in their own Git configuration, as the floor design decides for the floor | passing `-c safe.directory=<the target>` on each read, which would let a hostile target run a filter under the auditor's own user; reading UNVERIFIED with no reason, which hides what to fix | agent | decided |

## Checks

A gate reads PASS or FAIL, UNVERIFIED where a fact it needs is not verified. A review reads PASS
where nothing matched, else UNVERIFIED with the line quoted and the hit's ruling id. The security checks answer to rule
S4 and report first; `retired-reference` and `stale-reference` answer to S14 and report next, `load-resolution` to S7 after it.

| Check | Observes | Kind |
| --- | --- | --- |
| `hidden-characters` | tag characters, zero-width and bidirectional controls, variation selectors (one after a symbol excepted), private-use and unassigned characters, a combining mark after ASCII, any non-ASCII in a URL or code span (a span wraps within its paragraph; fenced code is none); a file left unopened reads UNVERIFIED; in an agents' note that no harness loads as an instruction file, a hit reads UNVERIFIED for that note; a binary file (an image, archive, font, video or PDF suffix, or a NUL byte) is not read and does not change the result, save one that a harness row loads as instructions or configuration, which reads a deciding UNVERIFIED | gate |
| `concealed-content` | HTML comments but OutcomeBound's block markers, each a comment alone on its line that is exactly a marker of the block grammar (`identity.SENTINEL_BEGIN`: begin, its id, an optional hash and its version; `SENTINEL_END`: end and its id; nothing else), so a comment that only starts like one is read as any comment and its line as any line; a marker is passed over as an HTML comment only: its line is read as any line, so an encoded run in its id, hash or version is judged as below, and a hash that is no sha256 digest (64 lowercase hex characters) or a version that is no dotted number is a hit; base64-shaped runs of 60 or more characters with no space, judged after each stretch of hex characters 40 to 44 or 64 to 68 long (a pin and at most 4 more hex characters, the largest seen in field hits) is taken out: a pin alone, after `name=`, or glued to a label or word is no payload; a hex stretch of 60 to 63 or 69 or more characters stays in and is flagged, as is a payload of 60 or more with a pin attached; pieces cut by pins or by any base64 character that is not hex read as pieces between spaces; a run that is not all hex counts only where a piece holds a stretch of 24 bytes of text (one stray character between stretches of 8 bytes or more joins them), as UTF-8 or as UTF-16 ASCII, its pieces' stretches of 8 bytes or more come to 24 together, or a piece starts a compressed stream; fetch-and-run lines | review |
| `override-phrases` | phrases that override earlier instructions, ask for secrecy, grant autonomy or plant memory | review |
| `harness-config` | in each configuration file a row names, keys holding commands, tool servers, all tool servers at once, endpoints or permission bypasses; TOML is read lexically, an unsettled value reading UNVERIFIED | review; a secret-shaped value is a gate |
| `instruction-change` | with `--base <ref>`, each file in scope, `.outcomebound/manifest.json` and `.outcomebound/retired.json`, changed between the ref and HEAD; a ref that does not resolve reads UNVERIFIED | review |
| `load-resolution` | per harness, whether its row is verified and inside its re-check date (past it, the fact names the day the row was verified and that only the re-check is due); where its configuration was read, one line naming the key categories the row leaves unsettled; each such UNVERIFIED does not change the result, save for a harness no row names; and each file the row's `ancestors` loads from a folder above the target, a review that does not change the result | gate that does not change the result |
| `retired-reference` | where `.outcomebound/retired.json` exists, each occurrence of an entry's term, path or command in a `.md`, `.mdc`, `.markdown`, `.txt` or `.rst` file Git lists, inside the list's `scope` where it names one, read by the rules of its decision row: the entry's `match`, word boundaries, prose only for a `term` entry, released changelog sections and the list's `history` and `allowed_in` files as history, quotes inside a `Changed —` line, and no managed block, recorded copy or ignored file; an unreadable or invalid list reads `UNVERIFIED`; a file it cannot read as text (not UTF-8, a NUL byte) reads `UNVERIFIED` and does not change the result | gate |
| `stale-reference` | in project-owned instruction text, each inline code span that is a concrete relative path, `make <target>`, or `npm run`, `pnpm run` or `yarn run` and a script name. Project-owned text is each Markdown file in scope (`.md`, `.mdc`) leaving out OutcomeBound's managed blocks, the skill and fragment copies the manifest records, and the agents' notes, plus the project's own `.outcomebound/fragments/local.md`; the manifest is the target's data, which a non-deciding finding may trust. A concrete relative path holds no whitespace or control character; does not start with `@`, `-`, `~`, `/`, a scheme (`x://`) or a drive letter; holds no `<`, `>`, `$`, `*`, `{` or `\`; ends in a file extension or in `/`, read without a trailing location (`:12`, `::name`, `#anchor`), so that a label such as `read/write` is none; is not in a sentence that names its owner as another project, by a capitalized possessive right before it (`Acme's`) or by a named repository (`the Acme repository at`), a determiner such as `this` naming this repository instead; and its first segment exists at the file's folder or at the root, so a Git ref, a package scope, a repository slug or a path in another repository is no reference, and neither is a path in `.git`, which the command never enters; a removed top-level folder is therefore missed. It is flagged where neither the file's folder nor the root holds it, Git does not ignore it (asked only where Git lists the target; where it cannot say, the path reads `UNVERIFIED`), and it resolves inside the target (one that resolves outside is skipped). A Make target is looked for in the nearest `GNUmakefile`, `makefile` or `Makefile` upward from the file's folder, then at the root, after flags and `VAR=` words are left out: a rule line or a `.PHONY` entry defines it; a `-C` or `-f` form, an `include`, a pattern rule or a rule named by a variable reads a target it does not show `UNVERIFIED`. A script is looked for in the nearest `package.json` upward, then the root; a target or script with no makefile or `package.json` at or above the file is flagged, and one whose file is not a regular file in the target, or no JSON object, reads `UNVERIFIED`; under `yarn run`, a name `package.json` does not define reads `UNVERIFIED`, since `yarn run` also runs a dependency's binary | review that does not change the result |

The files read are those each selected row says its harness loads: root and nested instruction
files, imports, project override files, rules and skill directories, and configuration. In a Git
work tree they come from what Git tracks or does not ignore, plus each path a row names exactly,
plus every file in `.agents/handoffs/` and `.agents/shared-memory/`; a target Git cannot list,
or ignores, is walked whole, and the report says which. Nested repositories and `.git` are not
entered, and no link is followed. A folder that cannot be listed is not entered and stops
nothing: in a walk of the whole target it is passed over, as Git's own listing passes it over;
in a note folder it is listed itself, so it reads UNVERIFIED unopened, as a linked folder does.

## Edges

It never opens a file the harness table records as one person's, by name or through a link, nor
anything outside the target but the engine's own data (above the target it only sees whether an
`ancestors` file exists) and the person's own rulings file, `~/.outcomebound/rulings.json`, which a
malformed or missing file leaves empty; a path it leaves unopened, a link out
included, reads UNVERIFIED. It never walks what Git ignores but those two note folders, never
runs, follows or obeys what it reads, and escapes quoted text so no file can steer the terminal.
For `retired-reference` only, it reads `.outcomebound/retired.json` and every file Git lists with the extensions that check names, inside the list's `scope`, as text; a target Git cannot list is walked whole, as for the other checks. Beyond the files in scope it reads, for `stale-reference` only, the project's `.outcomebound/fragments/local.md` and the makefiles and `package.json` files it looks targets and scripts up in, as text; it runs none of them. Its one process is Git, to list the files, to ask which candidate paths it ignores, and for `--base`: from PATH's absolute entries, with
no pager, fsmonitor, external diff or textconv, and no time limit. It opens no connection, rules no
hit benign itself, applies no edit and gives no score; `check` writes nothing, and `rule` writes
only the person's rulings file.

A clean pass does not rule out an injection: the lexical checks claim only the classes they
list, and `load-resolution` trusts the table, never watching a harness load. The steps it
prints are the person's to run, sandboxed.

What each verdict reads, and who writes it (`outcomebound_tools/instruction_audit.py`). The
instruction files, settings and skills in scope are the target's, which the change under check
can write; every check reads them, and nothing in them removes a hit. Which harness rows apply
comes from `--harness`, which the caller names, else from the manifest, which the change can
write: each row that loads a file the target holds and no row so far covers is added to it
(`manifest+present`), so an edit to the manifest cannot take a file a harness loads out of the
read. The retired list is the target's own data too: a change can remove an entry or widen its
`history` or `allowed_in` patterns, and so pass `retired-reference`. That is accepted, since the
check keeps a project's own prose in line with its own decision and guards no secret; with
`--base`, `instruction-change` names each change to the list, so a reviewer sees an entry go.
A person's rulings decide only whether the review hits they name change the result: the person
writes them, outside the target, and a change to a hit's file makes its ruling match nothing.
The harness table and the rule ids are the engine's (`adapters/harnesses.json`,
`docs/prompt-standard.md`). The agents' notes are written by agents in a session, not by a commit.

## Exits

0 PASS; 1 FAIL, on any gate FAIL; 2 UNVERIFIED, on any review hit or unverified fact, or a usage
error, as in the other verbs: exit 2 means a fact was not settled, not that a gate failed, and the text report of an UNVERIFIED result says so on its own line ("nothing failed"). A finding that does not change the result (`decides: false` in the report, "(does not
change the result)" in the text) is reported and leaves the exit as it is; a review hit a person
ruled safe is one, and so is each `load-resolution` UNVERIFIED about a row of the harness table, which nothing in the target settles; a harness no row names still changes the result.
Where every finding that holds exit 2 is a review hit with a ruling id, the text report says on its
own line that a person's ruling or a change to the hit's file settles it, and that running `check`
again settles none of them. `rule` exits 0 when each hit it asked about was recorded or declined, and 2
without a terminal, on an id that names no current review hit, or on a rulings file it cannot
read. `--strict` counts
UNVERIFIED as FAIL; `--json` prints one report (`schemas/instruction-audit-report.schema.json`);
`--verbose` adds the checks that passed. A report of `--only retired-reference` holds one PASS for each file read, one FAIL for each occurrence, a problem with the list at `.outcomebound/retired.json:0`, a header whose file count is the files this check read where no security check ran, and no steps "for the person to run", since its fixes are edits to the project's own text.

## Validation
