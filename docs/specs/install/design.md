# Install — design

## Outcome

An adopter runs one command, `outcomebound adopt`, and every harness they use loads the
operating contract, the facts that settle work in this project, and a pointer to each piece of
guidance with the condition that calls for it. Running it again from a newer release is the
upgrade; `--check` says whether the install is current; `--remove` takes it out. `--facts-only`
installs the project's facts alone, without the contract and pointers (section Facts-only). How:
`outcomebound_tools/adopt.py`, `outcomebound_tools/facts.py`, `outcomebound_tools/fragments.py` and `outcomebound_tools/textio.py`;
how `outcomebound` is installed and launched is the [distribution design](../distribution/design.md).

## What AGENTS.md carries

Three managed blocks, in this order: the kernel; `project-facts`; `guidance-pointers`. The facts
and pointers blocks carry `v=1.0.0`, a sentinel no reader compares, and no `hash=`: the manifest
records each block's digest.

`project-facts` is one line per fact, `- <label>: <fact>`, the fact verbatim. A fact the engine
cannot observe is left out, and the install report names it `UNVERIFIED`. A fact the engine read
every place for and found absent (no CI file it reads, no Setup recorded, no edge declared and no
floor) is left out too, and the report names those on one `note` line, `left out: ...`, each with
what records it; Done stays `UNVERIFIED` when none is recorded, since it is the full suite the completion bar names.
The report restates these facts only on a run that changes a file: a
run with nothing to change prints `nothing to change` and no restated fact.

| Fact | Source | Left out when |
| --- | --- | --- |
| Done | the commands `--done` recorded, in run order, each in its own code span, joined as `a`, `b` and `c`, then `(the full suite: run it where focused checks do not cover the changed risk, or the project's own instructions require it)`, which ties it to the kernel's completion bar: run where the changed risk reaches it or the project requires it, and then every one must pass (`facts.done_line`) | none is recorded |
| Setup | the commands `--setup` recorded, in run order, each in its own code span, joined as `a`, `b` and `c`: the person's record, which adopt never runs | none is recorded |
| CI test | each test command a `.github/workflows/*.yml` `run:` step or a `.gitlab-ci.yml` `script:` entry runs, as it runs from the root: a step's `working-directory:`, else its job's or the workflow's `defaults.run.working-directory:`, becomes `cd <dir> && `; each file's commands followed by the file | no command is read; a command the reading cannot settle (an expression, a `cd` earlier in its step or job, a folded, multi-line, flow or alias value, a link) is left out and named, and the file's other commands are kept |
| Irreversible edges | each selected fragment's `edges:`, once each, then `loosening the quality floor` where `.outcomebound/floor.json` exists | none is declared |
| Text for people | the style `--human-style` recorded: `ste` asks for documents a person keeps (pull request descriptions, commit messages, specs and handovers) in ASD-STE100 Simplified Technical English style, and not for replies in conversation, quoting none of the standard, with no length limit and every fact kept; in a report, brief, handover or request description an id or label the person has not used is explained or left out, and a hash or digest is given as a ref, version or path, save one a check or the project's rule requires (a `ruled <id>` line, a revert). It reaches only a project that records the style | none is recorded |
| Precedence | these facts over any other repository text that disagrees, and the person's instruction in the session over these facts; the project's own instructions in `AGENTS.md` and each selected harness's import host that exists over OutcomeBound's; process a project document only suggests is sized like any other step. A facts-only install stops after the first two clauses, since it installs no OutcomeBound guidance to rank | never |

A test command is a runner named as a whole word or command (`pytest`, `make test`, `npm run
test:ci`, `bash scripts/run-tests.sh`), after wrappers such as `uv run` or `npx`; `make
test-data` and `npm run test:watch` are not.

Detection keeps the observed CI test commands separate from its Done candidates. Done runs
through POSIX `sh`. A GitHub Actions step is a candidate only where its shell reads as `sh` or
`bash`: the step's `shell`, then the job's `defaults.run.shell`, then the workflow's default,
then a known hosted runner's default. Windows defaults to `pwsh`; Ubuntu and macOS default to
`bash`. A dynamic, custom or unreadable shell or runner is unsettled. GitLab script entries do
not establish the runner's shell. These rules follow
[GitHub's shell and defaults contract](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsshell).

Other CI commands stay in the CI test fact. Detection says they were not copied into Done and
asks for a project POSIX equivalent. A command found independently in the project's test
configuration can still be proposed, marked as a host candidate rather than a CI command.
Neither a `bash` shell nor a lexical reading proves compatibility with `sh`: Bash syntax,
CI-only variables, tools and setup still need project review. Detection runs no command and
does not change or refuse a Done command the user already recorded. No shell translation or
new runtime is added, and the installed block and manifest formats do not change.

The facts record holds the selection (`harnesses`, in the order named, and `fragments`), the `done` commands, the `setup` commands, any `style`, any `mode`, and `inputs`: each source
path read, with its sha256. A run reads the harnesses from it; for a manifest written before it
held them, from the skill records. `--check` recomputes the block: bytes other than both the record's and
the recomputation's read `edited`; a record other than the recomputation reads `stale`, naming each
fact that moved and each input that changed, or, where the bytes are the recomputation's, saying
so. `--check` also plans the install the recorded selection and mode give, writing nothing: each
record it would hold that the manifest lacks reads `missing`, and each record the manifest holds
that it would not hold reads `stale` where its bytes are current, saying that the install removes
it, so a record set that is not the recorded mode's never reads `current`.

### Facts-only

`adopt --facts-only` installs the facts a project would fumble without and none of
OutcomeBound's general guidance. `AGENTS.md` carries the `project-facts` block, then, where the
`local` fragment is selected, a `guidance-pointers` block that holds the `local` fragment inline
and nothing else. It carries no kernel block, no fragment pointer and no skill pointer, and the
install copies no fragment to `.outcomebound/fragments/`. The fragment selection is still
recorded and still feeds the Irreversible edges fact. Skills are installed only for a harness
whose row records `native_skills: true`, at that harness's skill path, where the harness lists
each skill by its description and loads its body only when a task calls for it; a harness without
native skills (`generic` among them) gets none, since nothing would point at them. The host
import block (`@AGENTS.md`), the `.outcomebound/.gitignore` record and, where the `workspace`
fragment is selected, `.agents/.gitignore` are as for a full install: they are not guidance.
The harnesses are recorded in the facts record, not only on skill records, so `generic`, which
gets no skill in this mode, stays selected: a later `--full` gives it its skills again, and the
instruction audit checks it as it checks a full `generic` install.

Precedence in this mode reads `these facts over any other repository text that disagrees with
them, and the person's instruction in the session over these facts`: the clauses that rank the
project's instructions over OutcomeBound's and size process name guidance this mode does not
install. Done keeps its parenthetical, since it says what this project's Done means: the full
suite, run where focused checks do not cover the changed risk. The `local` fragment is the
project's own text and is inlined verbatim; since no registry or skill explains a mechanism id in
this mode, a facts-only project writes its Mechanisms line in plain words, the condition and the
act, and backticks no id it needs a reader to understand.

The mode is recorded in the facts record as `mode: "facts-only"`; a record without `mode` is a
full install, and a record whose `mode` is neither `full` nor `facts-only` is refused, as any
malformed record is. Omitted, a run keeps the recorded mode, so the upgrade stays facts-only;
`--full` returns to a full install. `--check` recomputes against the recorded mode, and a
facts-only install whose files and records match it reads `current`. `--detect` proposes no mode.

An engine before this mode does not know the field: its `--check` reads the facts block of a
facts-only install `stale` (its Precedence line is the facts-only one), and its next install
writes the full install and drops `mode`. A project that uses this mode therefore moves every pin of the engine (CI, each machine,
each cloud setup step) to a release that knows it before it installs facts-only; the adopter steps
of the release that ships the mode say so. The manifest stays format 2, for the reason the
decision on `frame` gives: a format 3 would break each machine and CI job that pins an earlier
engine, a facts-only install or not.

`guidance-pointers` holds the `local` fragment inline first, since only its author knows which of
it every task needs; then `- <condition>: read <path>` per selected fragment, the path a verbatim
copy at `.outcomebound/fragments/<id>.md` recorded as kind `fragment`; then one line per skill the
install carries, naming its `SKILL.md`. A fragment has a five-slot body and two optional
frontmatter fields: `condition:`, one line; `edges:`, a JSON list, each shipped fragment declaring
edges only where its text names an act irreversible, in words the fragments share so the union
names each act once, and only for an act every project that selects it can take: publishing is
declared by `ci-release`, never by a stack fragment, whose body names it only where the project
publishes. A fragment has no `skills:` key: no fragment adds a skill.

The same rules hold for the project's own `local` fragment, which starts from
`templates/fragment-local.md`, and a parse refuses a fragment that breaks one, naming the rule:

- The body holds all five slots, Context, Bounds, Mechanisms, Completion bar and Distinguish, in
  that order, each line starting `**<slot>** — `, and nothing before the first. A slot with
  little to say stays, short.
- On the Mechanisms line, only a mechanism id of the registry takes backticks: every backticked
  token there is read as one. A command or any other name is written without them.
- An edge is one line and holds no `;`: the Irreversible edges fact joins the edges with `; `, so
  such an edge would read as two.
- A list-valued key (`detect:`, `edges:`) takes one form, a JSON list on the key's own line,
  each item in double quotes. A parse refuses any other form (a YAML block list, a flow list
  with unquoted items, one bare value, no value, a comment or a continued line) and names the
  lines it read, the key's line and every line after it up to the next line that opens a key
  (a block list's items, a flow list's continued lines and its closing `]`, at any indent), with the form
  by example, as `edges: ["pushing a tag", "publishing a release"]`. It suggests no corrected
  line.
`fragments compose` renders both blocks a full install writes for a selection, never a
facts-only install's; `--inline` emits the kernel, the skills an install carries and the fragment
bodies, for a delegate's role prompt.

## Onboarding

Onboarding is everything from first contact with a repository to the point where any agent in it
has correct, verified and minimal project facts. Measured studies of context files found that an
overview generated from the repository gave no reliable gain and cost more, and that commands a file
names are the commands agents use; so onboarding writes no overview. It records facts a check can
show, records the Done commands, proposes only the lines an agent would
otherwise get wrong, each with the file that shows it, and asks the person only what the repository
cannot show. The procedure is the `adopt-outcomebound` skill, in the engine's own files
(`$(outcomebound home)/skills/adopt-outcomebound/SKILL.md`); the engine supplies the facts. A new
project starts from the same command on an empty repository, and its route is the
`using-outcomebound` skill's new-project reference.

## Edges

Writes stay inside the target and go through `fileplan.write`: never through a symlink (on Windows, nor a junction), never into
`.git` in any spelling, staged and renamed atomically, and refused when a file changed after it was
read. The change is checked before the first write and again just before each rename, and before
each retry of a rename that Windows refused for a moment; that is a recheck, not a compare-and-swap,
so an edit in the instant between the last check and the rename is still overwritten. A destination expected absent is created exclusively, so a file that appears in
that instant is refused, not overwritten (the [scaffold design](../scaffold/design.md)). A staging file left by an earlier run is refused before the first write and never
removed; a failed write removes only the stage it created, so a stage name that another writer took
after the rename, or that a folder changed into a link reaches, is left; and a failure after the first write does not roll the earlier files back. Every byte adopt did not write is preserved, save a settings document's whitespace and an
empty `hooks` object or event list (`Stop`, `UserPromptSubmit`) it had, which `--remove` deletes; `--remove` restores a file
adopt created or extended to what it held before: the fragment copies, the skill folders and
`.agents/.gitignore` and `.outcomebound/.gitignore` go, the project's own `local.md` stays. Reading a fact runs nothing from the
target.

A project can edit a rendered block and its source in the same way, while the release also
changes how that block renders. For the `guidance-pointers` block and the `local` fragment it
inlines, adopt decides each case without `--force`:

| Block bytes on disk | adopt |
| --- | --- |
| equal to the record | updates it |
| equal to the new render | records it, on a `kept` line |
| equal to neither: the source's edit, rendered by the release that wrote the record | updates it, on a `render` line |
| equal to neither: a person's edit | refuses without `--force` |

The record's `frame`, or for a record without it the local fragment's earlier text in Git, tells
the last two rows apart. A record without `frame` whose earlier fragment text Git does not hold
reads as a person's edit, so it is refused without `--force`. `tests/test_upgrade_corpus.py` holds each
row, from 1.0.0 and from the newest release, with a candidate that renders the block anew.

## Install diagnostics

Ignored-file diagnostics inspect the final managed paths and manifest on every install and
dry run, including a repeat that changes no bytes. Removed and unmanaged paths do not enter
that inventory. A warning changes no ignore rule, index entry, project file or native trust.
Untracked files alone do not make a machine-local install invalid.

Repeat adoption without a harness selection keeps the recorded harnesses. Skill paths can sort in
a different order from the original harness selection; that difference must not rewrite an
otherwise unchanged manifest.


## Install survival

An install that is only in a working tree can be lost: a stash can take away a tracked file's
changes, and a branch switch can replace them. A worktree made from a commit without the install
has none. A session that already loaded the instructions keeps them, so the files on disk and
the guidance in a session are separate facts: `--check` reports the files, and never says that a
session did or did not load the contract. It reports; it commits, restores, stashes and upgrades
nothing.

- A record line that reads `missing` for a block or file says `expected block missing on disk`
  (or `expected file`) and whether HEAD's commit holds it. Where HEAD's commit does not hold it
  either, the line says that a stash or another branch may: a synthetic example is an
  uncommitted block that a cleanup stash took away.
- A target with no manifest says on its `missing` line whether HEAD's commit holds the manifest:
  a worktree made from a commit before the install reads `HEAD's commit does not hold it either`.
- One `warn` line, `not committed: ...`, names each block and the manifest whose bytes on disk
  HEAD's commit lacks or holds otherwise, counts the other files, and gives the total. Bytes are
  compared with CRLF as LF, as the records are. The line says that a new worktree from HEAD does
  not hold these bytes, and that whether a stash or a branch switch takes them away depends on
  the paths and the options: a plain stash leaves an untracked file, and a branch switch can keep
  a local change.
- A facts-only install prints one `note` line that says that `AGENTS.md` holds no operating
  contract by intent, so a reader does not take the absent block for a lost one.
- For each other worktree, the worktree `warn` line adds each block and file missing on disk,
  grouped by whether its commit holds it, what its commit does not hold as on disk, or, with no
  manifest on disk, whether its commit holds one.
- A path that cannot be read, on disk or in the commit, reads `install state UNVERIFIED: cannot
  read <path>`, and a manifest that does not parse reads the same with the reason. Such a read
  never stops the check or changes its exit, so a worktree that another task owns cannot fail the
  check of a healthy one.
- Git is asked read-only: optional locks off and no lazy fetch (`GIT_OPTIONAL_LOCKS=0`,
  `GIT_NO_LAZY_FETCH=1`, as `where` and `size` ask it). HEAD's paths come from `git ls-tree`, and
  their bytes from `git cat-file --batch`; a path the tree lists whose bytes this clone does not
  hold, as in a partial clone, reads `UNVERIFIED`, never "not in the commit".
- `outcomebound where` runs the same survey for the current checkout and names a problem on a
  `git` line, `this checkout: ...`. A checkout with no install whose commit holds none gets that
  line only where another worktree has an install, so a project that never adopted OutcomeBound
  gets none.
